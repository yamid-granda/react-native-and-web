This command invocation explicitly requests the repository's start-task workflow. Read and follow `.agents/skills/start-task/SKILL.md`, `.agents/rules/git-model.md`, `.agents/rules/no-auto-commit.md`, and `.agents/agents/git-ops.md`.

Follow any additional scope or instructions here: $ARGUMENTS

Use the `git-ops` agent for the git operations that create the work tree; it is pinned to the Space Bunny Free model required by `.agents/rules/git-model.md`, so do not run those git commands inline. Create the new work tree first, then launch `opencode --auto` in a terminal inside it and confirm the prompt was accepted before making any edit here. The work tree the session started in — including `main` — is read-only: never implement the task there and never copy the finished files over afterwards.

The console execution of `opencode --auto` must happen in the **new** Orca work tree tab, not in the current tab. Create the work tree with `orca worktree create`, then `orca terminal create --command "opencode --auto"` inside it — not `worktree create --agent opencode`, which starts plain `opencode` without `--auto`. Wait for `--for tui-idle` before sending the task instructions, and only send when the wait reports `satisfied: true`; a timeout arrives as `ok: false` with `error.code: "timeout"` instead. An `orca` on `PATH` may be a stale symlink that still exits `0`, so treat `Unable to determine Orca.app path from symlink` as "no CLI" and fall back to `/Applications/Orca.app/Contents/Resources/bin/orca`. When no Orca CLI answers at all, take the documented git fallback and implement the task in this session after moving it into the work tree.

Work through the workflow in order: preflight the existing work trees and resolve the Orca CLI, derive the `<owner>/<type>-<summary>` branch and the sibling work tree path from the instructions, create the work tree from `origin/main`, launch the agent in the new work tree and verify the handoff, then stop. Being called from `main` or from another task's work tree changes none of this — it still gets its own new work tree. If the instructions are too vague to name a task, or the derived name already exists as a branch or a directory, stop and ask instead of guessing. Never commit or push — the user reviews the changes first, then lands them with `/cc-commit-and-push` or `/cc-accept-work-tree`. Report the branch, the work tree path, the base ref, the new terminal handle, that the task was handed off to that tab rather than run here, that the calling work tree was left untouched, and the checks you ran or could not run.
